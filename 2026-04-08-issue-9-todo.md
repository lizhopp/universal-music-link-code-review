## What Already Exists

### Working Pieces

- `server/.env` exists locally
- backend scripts load env values with `--env-file=.env`
- current backend can start locally with the existing env file

### Evidence In Code

- `server/package.json`
  - `start`: `node --env-file=.env server.js`
  - `dev`: `nodemon --env-file=.env server.js`
  - `db:seed`: `node --env-file=.env db/seed.js`

- `server/db/client.js`
  - reads `process.env.DATABASE_URL`

- `server/utils/jwt.js`
  - reads `process.env.JWT_SECRET`

- `server/app.js`
  - reads `process.env.CORS_ORIGIN`

- `server/server.js`
  - reads `process.env.PORT ?? 3000`

## What Is Missing

### 1. No `.env.example` file yet

This is the biggest missing piece.

Right now a new developer has to infer the needed variables from:
- code
- README
- trial and error

That is exactly the kind of friction issue `#9` is supposed to reduce.

### 2. No fail-fast env validation

The app currently reads environment variables directly:
- `DATABASE_URL`
- `JWT_SECRET`
- `CORS_ORIGIN`

But nothing checks them up front and throws a clean setup error before the app starts doing real work.

That means if one is missing:
- the error may appear later
- the message may be less beginner-friendly
- it can be harder to tell whether the problem is env setup, DB config, or route logic

### 3. Docs are incomplete for the real current setup

The README currently documents:
- `DATABASE_URL`
- `JWT_SECRET`
- `SPOTIFY_CLIENT_ID`
- `SPOTIFY_CLIENT_SECRET`

But your backend code currently also uses:
- `CORS_ORIGIN`

And the server also supports:
- `PORT` as optional with a fallback to `3000`

So the docs are not fully aligned with the code.

### 4. Current env requirements are mixed with future env requirements

Right now the README mixes:
- variables currently required by running code
- variables that are probably for future Spotify API work

That makes setup feel more confusing than it needs to.
